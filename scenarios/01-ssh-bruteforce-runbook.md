# Runbook. Сценарий 1 «Брутфорс SSH» — чистый прогон со скриншотами

Пошаговый порядок выполнения сценария от начала до конца. У каждого ключевого
экрана указано имя файла скриншота для папки screenshots/.

Условие: стенд уже настроен (rsyslog + чтение /var/log/auth.log,
PerSourcePenalties no, снят rate-limit journald, добавлены правила).
Атакующий Kali — 192.168.56.102, цель SOC_LAB — 192.168.56.10.

---

## Часть 0. Подготовка

1. Запустить обе VM: SOC_LAB и Kali.
2. Открыть дашборд https://192.168.56.10, войти.
3. Вкладка Threat Hunting → События.
4. Период (справа вверху) — Последние 1 час.
5. Включить авто-обновление (каждые 10 сек).

Чтобы не ловить глюк интерфейса (removeChild): не дёргайте фильтры по
одному. Если нужно сбросить вид — жмите F5 и ищите через строку поиска
по rule.id, а не через фильтры.

---

## Часть 1. Проверка связности (на Kali)

```bash
ping -c2 192.168.56.10
nc -zv 192.168.56.10 22
```
Ожидается: пинг проходит, порт 22 open.

01-01-connectivity.png — терминал Kali с успешным ping и 22 ... open.

## Часть 2. Атака — подбор пароля SSH (на Kali)

Список паролей (если ещё не создан):
```bash
for i in $(seq 1 20); do printf 'wrong%02d\n' $i; done > /tmp/mini3.txt
```

Запуск перебора:
```bash
hydra -I -l nikolay -P /tmp/mini3.txt -t 4 ssh://192.168.56.10
```
Ожидается: 20 login tries ... 0 valid password found (пароль не подобран — цель
не взлом, а детект).

01-02-hydra.png — терминал Kali с выводом hydra (видно цель, число
попыток, completed).

## Часть 3. Подтверждение на сервере (на SOC_LAB)

Это надёжное текстовое доказательство, не зависит от интерфейса.

Факт неудачных входов в системном логе:
```bash
sudo grep "Failed password" /var/log/auth.log | tail -n 10
```
01-03-authlog.png — строки Failed password for nikolay from 192.168.56.102.

Срабатывание правил Wazuh:
```bash
sudo grep -c "Rule: 5712" /var/ossec/logs/alerts/alerts.log
sudo grep -A3 "Rule: 5712" /var/ossec/logs/alerts/alerts.log | tail -n 20
```
Ожидается: счётчик 5712 больше 0, и блок алерта с описанием
«sshd brute force trying to get access» и srcip: 192.168.56.102.

01-04-alerts-5712.png — вывод с правилом 5712.

## Часть 4. Отображение в дашборде (SOC_LAB)

### 4.1. Лента событий атаки
В строке Поиск ввести:
```
rule.groups:sshd
```
Enter. Видна серия 5760 и всплеск на гистограмме.

01-05-events.png — список событий sshd + столбик всплеска.

### 4.2. Детект брутфорса (главный кадр)
Очистить поиск, ввести:
```
rule.id:5712
```
Enter. Раскрыть событие (иконка слева) — видны поля srcip, rule.level,
rule.mitre.id: T1110.

01-06-rule5712.png — развёрнутое событие 5712 с полями (главный кадр).

### 4.3. Матрица MITRE ATT&CK
Меню (☰) → MITRE ATT&CK. Видна техника T1110 (Brute Force) со счётчиком.

01-07-mitre.png — техника T1110 в матрице.

---

## Если 5712 не появился

1. Проверить счётчик на сервере: sudo grep -c "Rule: 5712" /var/ossec/logs/alerts/alerts.log.
   - > 0, но в дашборде пусто → нажать Обновить / F5 (кэш интерфейса).
   - 0 → повторить атаку (Часть 2). Порог 5712 — ≥8 неудач за короткое время;
     20 попыток при отключённом PerSourcePenalties его набирают.
2. Глюк removeChild в UI → F5, не трогать фильтры, искать через rule.id.
